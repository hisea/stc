# STC 规范性用语强度审计

**基线：Draft 0.4.5**

本审计用于检查 STC 从旧的“应 = 推荐要求”迁移到 GB/T 1.1-2020 风格“应 / 不应 = 要求，宜 / 不宜 = 推荐”后，是否出现义务强度被静默提升的问题。

## 判断原则

- **要求（应 / 不应）**：不满足时会造成技术含义、逻辑边界、对象、数值、引用、安全或可验证性缺陷。
- **推荐（宜 / 不宜）**：存在明确偏好，但仍有其他合理且不损害技术含义的表达方式。
- **拆分**：同一规则同时包含“必须满足的语义底线”和“优选写法”，不应只用一个强度词覆盖。

本审计只评价规范性强度，不评价规则是否属于未来的 Core / Standard / Machine-Ready。

## 结果摘要

| 结论 | 规则数 |
|---|---:|
| 保持为要求 | 88 |
| 保持为推荐 | 4 |
| 建议降为推荐 | 17 |
| 建议拆分 | 3 |
| **合计** | **112** |

## 优先处理的迁移项

以下规则最容易因为“应”的新定义而被无意升级，建议在进入 Draft 0.5 前先处理：

1. **STC-005**：`应优先使用直接动词` → `宜优先使用直接动词`。
2. **STC-006**：删除形式词宜作为推荐；造成歧义时再由更具体规则判为不合规。
3. **STC-401**：拆成“歧义时应拆分 / 仅复杂时宜拆分”。
4. **STC-501**：条件前置改为推荐，条件作用范围明确仍由 STC-502 强制保证。
5. **STC-601**：否定词靠近改为推荐，否定范围明确作为要求。
6. **STC-1005**：中英文空格和稳定排版明确降为推荐。
7. **STC-1601 / STC-1602 / STC-1603**：把列表风格偏好和逻辑要求分开。
8. **STC-1701**：唯一正式术语用“应”，多个允许术语的首选关系用“宜”。
9. **STC-1802 / STC-1803**：把“产生歧义”和“阅读负担”分开。
10. **STC-2101 / STC-2103 / STC-2206 / STC-2401**：这些主要是 UI、错误文案和版式偏好，建议使用“宜”。

## 版本记录建议

Draft 0.4.4 引入 GB/T 风格规范性用语后，应在 CHANGELOG 中明确记录：

> 旧草案曾将“应”定义为推荐性要求。Draft 0.4.4 起，“应 / 不应”改为要求，“宜 / 不宜”改为推荐。为避免义务强度静默变化，Draft 0.4.5 后对所有规范性条款进行逐条强度审计。

在审计完成前，不宜把 0.4.4 的机械迁移视为规则强度已经冻结。
